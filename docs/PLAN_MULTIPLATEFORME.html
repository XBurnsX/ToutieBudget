0. Règles pour les IA (Claude et Codex)

0.1 Une étape à la fois

  1. Ne travailler que sur la première étape non terminée du tableau d'avancement (section 5). Ne jamais commencer l'étape N+1 avant que l'étape N soit marquée « Fait » avec son commit.
  2. Avant de toucher un fichier, relire la section de l'étape en entier, puis l'état réel du dépôt (git status, git log -5). Si l'état réel ne correspond pas à ce que l'étape suppose, s'arrêter et le dire à l'utilisateur.
  3. Ne faire que ce que l'étape décrit. Aucun « tant qu'à y être » : pas de renommage, pas de nettoyage, pas de refonte hors liste.
  4. Si une instruction est ambiguë, impossible ou contredite par le code, s'arrêter et poser la question. Ne jamais déduire une règle financière.

0.2 Règles financières non négociables

  1. Aucun argent ne doit apparaître ou disparaître. Toute opération respecte les invariants de l'étape 7.
  2. Une refonte qui change un résultat de calcul existant (même d'un cent) est un échec : on s'arrête, on ne corrige jamais un test de référence pour le faire passer, sauf si l'utilisateur l'a demandé par écrit.
  3. Aucune valeur inventée : un taux, une durée, une date absente donne « indisponible », jamais une valeur par défaut.

0.3 Règles du dépôt (déjà en vigueur, à respecter strictement)

  • Pousser seulement sur main, remote ToutieBudget : git push ToutieBudget HEAD:main. Pousser seulement quand l'utilisateur dit de pousser.
  • Ajouter les fichiers un par un, par chemin explicite (git add chemin1 chemin2). Jamais git add ., -A ou un joker.
  • Ne jamais commiter : le changement de versionCode/versionName dans app/build.gradle.kts (sauf à l'étape 0 où on ne touche pas ces lignes), qa/, ToutieBudget-AutoTester/, .idea/deploymentTargetSelector.xml, *.apk, pb_import/, tests-en-direct.ps1, keystore.properties, *.jks, local.properties.
  • Avant chaque commit, vérifier qu'aucun changement d'une autre personne n'est mélangé (git diff --stat) ; ne jamais commiter un fichier modifié par l'utilisateur sans son accord.
  • Ne jamais construire d'APK (assembleRelease/assembleDebug) sans demande explicite de l'utilisateur.
  • Ne jamais lancer d'émulateur ni installer sur un téléphone sans demande explicite. Les vérifications « sur l'appareil » sont faites par l'utilisateur (il lance l'app depuis Android Studio).
  • Ne jamais saisir de mot de passe, de jeton ou d'identifiant. Les actions sur le serveur PocketBase (admin, Docker) sont faites par l'utilisateur ; l'IA fournit les commandes exactes.
  • Avant toute étape qui touche le serveur (6b, 8, 9d, 11) : l'utilisateur confirme qu'une sauvegarde de PocketBase vient d'être faite. Sans cette confirmation, on n'avance pas.

3. Conventions obligatoires

3.1 Langue et noms

  • Noms de classes, fonctions, variables et commentaires en français, comme le code existant (MoteurDette, soldeActuel…).
  • Package racine du module commun : com.xburnsx.toutiebudget.shared.

3.2 Argent

  • Tout montant stocké, transmis ou comparé dans shared est un Montant en cents (Long).
  • Les calculs d'intérêts et de pourcentages peuvent utiliser Double en intermédiaire, puis passent obligatoirement par ArrondiMonetaire.versCents(valeurDollars: Double): Long (demi vers le haut, identique à BigDecimal.valueOf(v).setScale(2, RoundingMode.HALF_UP)) aux mêmes endroits que le code actuel arrondit au cent.
  • Arrondi « au cent supérieur » (minimum de carte) : ArrondiMonetaire.versCentsSuperieur, identique à RoundingMode.CEILING.
  • Le serveur et Room gardent pour l'instant leurs champs en dollars (Double) : conversion cents = versCents(dollars), dollars = cents / 100.0 seulement aux frontières (adaptateurs).

3.3 Taux

Taux = pourcentage annuel en Double (ex. 14.99 pour 14,99 %). Toujours validé 0.0..100.0 et fini.

3.4 Dates

  • kotlinx-datetime uniquement dans shared (Instant, LocalDate, TimeZone).
  • Mois budgétaire : type propre MoisBudgetaire(annee: Int, mois: Int) (1..12), format texte AAAA-MM. Ne pas utiliser un YearMonth de bibliothèque.
  • Format texte des dates : AAAA-MM-JJ (comme MoteurCarteCredit.lireDate/ecrireDate).
  • Fuseau par défaut : America/Toronto. Une date tirée de « maintenant » se calcule toujours avec le fuseau de l'utilisateur, jamais avec celui du serveur (UTC).
  • Trois notions distinctes, jamais confondues :
    • enregistre_le : instant UTC où le serveur enregistre l'opération (généré par le serveur) ;
    • date_locale : date financière choisie par l'utilisateur (une dépense saisie aujourd'hui peut dater d'il y a trois jours) ;
    • mois_budgetaire : toujours MoisBudgetaire.de(date_locale), jamais tiré de enregistre_le.
    fuseau est enregistré pour savoir comment date_locale a été obtenue quand elle vient de « maintenant ».
  • Le temps courant vient d'une Horloge injectée (tests déterministes).

3.5 JSON

kotlinx.serialization dans shared. Les noms de champs JSON envoyés au serveur sont en snake_case, comme aujourd'hui (@SerialName("solde_dette")). Les champs JSON existants des détails (details_carte_json, details_dette_json, details_investissement_json) gardent exactement leurs noms de clés actuels (camelCase produit par Gson aujourd'hui) : vérifier par un test qui relit un JSON produit par le code Gson actuel.

3.6 Identifiants

Nouveaux identifiants : 15 caractères [a-z0-9] (compatibles PocketBase). operationId d'une commande : même format. Ouvertures : identifiant déterministe décrit à l'étape 6b.

3.7 Tests

  • Chaque moteur migré garde ses tests JVM dans app et reçoit une copie dans shared/src/commonTest avec les mêmes valeurs attendues.
  • Tests de date : jamais dépendre du jour réel ; toujours une Horloge fixe ou des dates explicites.

6b.6 Ouvertures (définition ; exécution à l'étape 9.6)

  • Une opération OUVERTURE par fiche projetée, d'identifiant déterministe : operation_id = "ouv" + premiers 12 caractères de sha256(utilisateur_id + ":" + collection + ":" + fiche_id + ":" + date_coupure) en hexadécimal minuscule (15 caractères au total).

  • Les transactions antérieures restent consultables mais ne produisent aucune ligne de journal.
  • Relancer la création des ouvertures ne crée rien de plus (unicité operation_id).

7.2 Invariants (vérifiés par shared ET par les hooks, nommés dans le contrat)

  1. Contrat : contract_version de la commande = version du serveur ; sinon 422 CONTRAT_INCOMPATIBLE.
  2. Unités : chaque variation est un entier, dans l'unité de son champ (6b.4) ; un champ en COMPTEUR ne reçoit jamais de cents et inversement.
  3. Propriétaire : toutes les fiches ciblées appartiennent à l'utilisateur authentifié.
  4. Idempotence : operation_id jamais appliqué pour cet utilisateur ; s'il l'est déjà, réponse « déjà appliquée » avec le résultat d'origine (pas d'erreur, pas de double).
  5. Révisions : chaque fiche ciblée a la revision attendue ; sinon CONFLICT avec les fiches canoniques.
  6. Champs autorisés : un type ne peut toucher que les couples (collection, champ) de sa ligne 7.1.
  7. Conservation budgétaire : pour ASSIGNATION, REPARTITION, VIREMENT_ENVELOPPES, RETOUR_PRET_A_PLACER, REPORT_MOIS : Σ des variations de pret_a_placer + Σ des variations de allocations.solde = 0. (Pour REPORT_MOIS, les variations de montant_reporte et d'alloue ne comptent pas dans cette somme : ce sont des traces, pas de l'argent.)
  8. Conservation bancaire : VIREMENT_COMPTES : Σ des variations de soldes bancaires = 0.
  9. Cohérence dépense : DEPENSE : −Δcompte.solde = Σ Δallocation.depense = −Σ Δallocation.solde.
  10. Dépassement : pret_a_placer après opération ≥ 0 pour ASSIGNATION/REPARTITION (comme aujourd'hui) ; aucun montant en dehors de ±10¹¹ cents.
  11. Date (MOIS_COHERENT) : date_locale valide ; mois_budgetaire = MoisBudgetaire.de(date_locale) ; toute allocation ciblée ou créée est de ce mois (sauf REPORT_MOIS : source = mois − 1, cible = mois). enregistre_le n'intervient jamais dans le mois.
  12. Créations : seules les collections de creations_autorisees ; toute fiche créée a ses valeurs projetées à 0 avant variations.
  13. Archivage et suppression : seulement par ARCHIVAGE_FICHE / SUPPRESSION_FICHE, et seulement si toutes les valeurs projetées de la fiche valent 0.
  14. Transaction : si cree_transaction, la fiche transactions écrite porte operation_id = celui de la commande, et son montant égale la somme des variations bancaires concernées.
  15. Blocage : si etat_journal.ecritures_bloquees = true pour l'utilisateur, toute commande est refusée (423 MAINTENANCE), sans rien écrire.
  16. Utilisateur passé au journal (etat_journal.journal_schema_version = 1) : toute création, modification ou suppression directe (hors route de commande) d'une fiche projetée ou d'un champ projeté est refusée.
